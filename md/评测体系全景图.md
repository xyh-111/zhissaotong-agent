# 评测体系全景图

> 把 Agent 的离线评测从「测试集设计」到「指标计算」到「真实教训」串起来。
> 核心结论：自建 42 条多场景测试集，跑一遍 Agent 采集工具调用/回答/延迟，用 LLM-as-Judge 打分 + 程序化比对，量化 7 项指标；过程中发现并定位了「幻觉率失真」这个评测设计缺陷。

## 图 2：单条用例的评测流程

```
_run_case（跑 Agent + 采集）
   │
   ├─ stream_mode=["updates", "messages"]  双模式流式
   │     ├─ updates 模式 → 抓「完整」的工具调用 + 最终回答（无 token 拼接问题）
   │     └─ messages 模式 → 抓首字延迟 TTFT（首个 model 节点文本 token 耗时）
   │
   ▼
_evaluate_case（打分，7 项指标）
   │
   ├─ 1. 任务完成率   ← LLM-as-Judge（judge_task_completion）
   ├─ 2. 幻觉率       ← LLM-as-Judge（judge_hallucination）
   ├─ 3. 工具准确率   ← 程序直接比对（预期工具 vs 实际工具+参数）
   ├─ 4. 检索命中率   ← 独立调 retriever，看是否命中关键词
   ├─ 5. 报告格式合规 ← 程序检查 Markdown 标题 + 报告/建议内容
   ├─ 6. 首字/端到端延迟 ← 打时间戳
   └─ 7. 工具调用次数   ← 统计 tool_calls 数量
```

**关键设计：三类指标用了三种不同的"裁判"方式**

| 类型 | 指标 | 判定方式 |
|---|---|---|
| 语义判断 | 任务完成率、幻觉率 | LLM-as-Judge（大模型当裁判） |
| 程序比对 | 工具准确率、检索命中率、报告格式 | 直接代码比对（最可信） |
| 性能测量 | 延迟、工具调用次数 | 打时间戳 + 计数 |

## 图 3：测试集设计（test_cases.json）

```
42 条用例，覆盖 5 类场景：

   选购咨询  12 条   （小户型/宠物/木地板/大理石/预算...）
   维护保养   8 条   （滤网/主刷/边刷/尘盒/电池...）
   故障排查  10 条   （迷路/回充/避障/漏扫/异响...）
   天气环境   4 条   （天气/湿度/降雨适配）
   报告生成   8 条   （生成报告/查询记录/分析数据）

每条用例的 schema：
{
  "id": "qa_01",
  "category": "选购咨询",
  "query": "小户型适合哪种扫地机器人？",
  "expected_tools": ["rag_summarize"],          ← 预期该调哪些工具
  "expected_tool_args": {...},                   ← 预期参数（宽松子串匹配）
  "reference_points": [...],                     ← 给裁判的参考要点
  "needs_rag": true,                             ← 是否需测检索命中
  "relevant_keywords": ["小户型", "选购"],        ← 检索命中的关键词
  "check_report_format": false                   ← 是否检查报告格式
}
```

**设计要点**：`expected_tools` 让"工具准确率"能程序化判断（不需要裁判）；`reference_points` 给裁判一个打分依据；`relevant_keywords` 让"检索命中"能落成可计算的标准。

## 指标详解（怎么测、样本多少）

| 指标 | 实测值 | 怎么测 | 样本 |
|---|---|---|---|
| 任务完成率 | 97.6% | LLM-as-Judge 对照参考要点判断是否完成任务 | 全量 42 |
| 工具选择/参数准确率 | 100% | 程序比对：实际调用的工具名+参数 vs 预期 | 需工具调用的用例 |
| 检索命中率（Recall@K 代理） | 93.3% | 独立调 retriever，看 Top-K 结果是否命中关键词 | RAG 用例 |
| 报告格式合规率 | 100% | 程序检查：有 Markdown 标题 + 含报告/建议内容 | 报告用例 |
| 幻觉率 | 59.5%（失真） | LLM-as-Judge 判断是否出现无依据事实 | 全量 42 |
| 平均首字延迟 | 14.66s | messages 流式模式打时间戳 | 全量 |
| 平均端到端延迟 | 40.64s | 计时 | 全量 |
| 平均工具调用次数 | 1.90 | 统计 tool_calls 数量 | 全量 |

## LLM-as-Judge 详解（judge.py）

两个裁判函数，都要求模型输出 JSON，并做了**容错解析**（`_extract_json`：先 `json.loads`，失败再用正则提取 `{...}` 块）：

```
judge_task_completion(query, reference_points, answer)
   → 判断"是否准确完整解决了用户核心需求"
   → 输出 {"completed": true/false, "reason": "..."}

judge_hallucination(query, reference_points, answer)
   → 判断"是否出现与参考要点矛盾/无依据的事实"
   → 输出 {"has_hallucination": true/false, "reason": "..."}
```

**LLM-as-Judge 的两个固有缺陷**（面试高频）：

1. **自我偏好**：用同款模型评自己的回答会虚高，严格做法换独立的更强模型 + temperature=0。
2. **信息不对称**：裁判只拿到"参考要点"，看不到工具返回的真实数据 → 容易误判。

## 真实教训：幻觉率为什么失真（重点）

**现象**：初版幻觉率 59.5%（25/42），高得离谱。

**定位**：查逐条裁判理由后发现，是**评测设计缺陷，不是模型真的幻觉**。典型例子——天气用例 `w_01`，裁判理由写着：

> "回答提供了参考要点未提及、无法由常识推断的具体数据，如 26°C、湿度 50%、AQI 21"

但这些数字恰恰是 `get_weather` 工具返回的真实数据。裁判看不到工具结果，只看到我写的概括性参考要点（"给出天气信息"），就把这些具体数字当成"编造"。

**按场景印证**：

| 场景 | 幻觉标注 | 根因 |
|---|---|---|
| 天气环境 | 4/4 全中 | get_weather 返回具体数字 |
| 报告生成 | 8/8 全中 | fetch_external_data 返回覆盖率/耗材数据 |
| 选购/维护/故障 | 约一半 | rag 带回超出参考要点的专业细节 |

**教训**：**评测指标本身的可靠性也要验证**——裁判的"参考答案"必须包含真实工具数据，否则测出来的数字是错的。正确做法是把工具返回结果也喂给裁判。

**这件事比"测了个高分"更值钱**：它证明你会质疑自己的评测结果、能定位根因，而不是拿到一个数字就写进报告。

## 一句话总述（可接住任何追问）

> 我自建了 42 条多场景测试集，跑一遍 Agent 用双模式流式采集工具调用、回答和延迟，再用三种方式打分——语义指标（任务完成、幻觉）用 LLM-as-Judge、确定性指标（工具准确率、检索命中、报告格式）用程序比对、性能指标打时间戳。实测工具准确率 100%、任务完成率 97.6%、检索命中率 93.3%。过程中发现幻觉率虚高，深挖后定位是裁判拿不到工具真实数据的评测设计缺陷，这让我意识到评测指标本身也要验证可靠性。
