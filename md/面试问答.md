# 智扫通智能客服 Agent — 面试问答文档

> 目标岗位：大模型应用开发（实习）
> 本项目的核心亮点：**ReAct Agent + RAG + 中间件动态提示词 + 自建评测体系**。

---

## 一、项目概述

**一句话简介**：面向扫地机器人的智能客服系统，基于 LangGraph 构建具备自主推理与工具调用能力的 ReAct Agent，结合 RAG 检索增强与场景化动态提示词切换，并自建评测体系量化 Agent 质量，前端 Streamlit 流式交互。

**技术栈**：Python、LangChain / LangGraph、ChromaDB、通义千问（qwen3.8-27b / qwen3.7-text-embedding）、Streamlit、YAML

**架构分层**：

```
app.py                 # Streamlit 前端
agent/
  react_agent.py       # ReAct Agent 编排
  agent_tools.py       # 7 个工具定义
  middleware.py        # 工具监控 / 模型日志 / 动态提示词
rag/
  rag_service.py       # RAG 总结链
  vector_store.py      # 文档加载 + 向量化 + 检索 + MD5 去重
model/factory.py       # 模型工厂（LLM / Embedding）
eval/                  # 评测模块（测试集 + LLM-as-Judge + 指标）
config/ prompts/ utils/
```

## 三、分主题面试 Q&A

### 3.1 Agent / ReAct

**Q1：ReAct Agent 和普通 LLM 调用有什么区别？**

普通 LLM 调用是"问一句、答一句"，模型只负责生成文本。Agent 则把大模型和工具串成一个"思考 → 行动 → 观察 → 再思考"的循环：模型不只是输出文本，还能判断"当前信息够不够回答问题"，不够就决定调用哪个工具、传什么参数，拿到工具结果后再判断是否需要二次调用，最后整合出最终回答。这个循环让它能完成"单靠一次生成完不成"的多步骤任务。

**Q2：模型是怎么决定调用哪个工具、传什么参数的？是代码里硬编码的吗？**

不是硬编码。靠的是 **Function Calling（工具调用）**：我在代码里用 `@tool` 给每个工具定义了 name、description、参数 schema，系统提示词里又详细写了每个工具的能力边界和使用场景，模型据此自主输出"要调用的工具 + 入参"。所以决策是模型做出来的，不是 `if/else`。

**Q3：如果工具调用陷入死循环怎么办？**（高频）

我在系统提示词里设置了硬性兜底：**最多 5 次工具调用**，5 次之后如果信息仍然不足，就直接回复"我不知道"。这样能避免 Agent 无限循环、白白消耗 token。

**Q4：怎么保证工具调用的入参正确？**

两件事：一是 Prompt 强约束——"入参必须与工具定义完全一致、字符串参数为纯文本、无额外引号"；二是用评测去验证——我单独设了"工具选择/参数准确率"这个指标，实测是 100%。

**Q5：你这个 Agent 里有哪些工具？分别是干嘛的？**

一共 7 个：
- `rag_summarize`：从向量库检索专业资料
- `get_weather`：查城市天气/湿度
- `get_user_location`：获取用户所在城市
- `get_user_id` / `get_current_month`：获取用户 ID / 当前月份
- `fetch_external_data`：查用户某月使用记录（做报告用）
- `fill_context_for_report`：触发上下文注入，为报告场景切换提示词

### 3.2 RAG 检索增强

**Q6：RAG 完整流程是什么？为什么要用 RAG？**（必考）

大模型有两个问题：知识有截止日期、会一本正经地编造（幻觉）。RAG 的思路是"外挂知识库"——把领域资料提前切好、向量化存进向量库，用户提问时先检索出最相关的几段，拼进 Prompt 让模型"基于参考资料回答"。

完整流程：**文档加载（PDF/TXT）→ 递归分片 → 向量化（embedding）→ 存入 ChromaDB → 提问时 Top-K 相似度检索 → 把检索结果作为上下文 → 模型总结生成**。

**Q7：分片的 chunk_size 和 overlap 为什么这么设？**

chunk_size=200、chunk_overlap=20。切太小语义不完整、检索结果碎片化；切太大检索颗粒太粗、相关度低。overlap 让相邻分片保留 20 字符重叠，避免把一句话从中间切断、丢失语义。

**Q8：Top-K 取多少？怎么定的？**

我取 k=3，检索出最相关的 3 段作为参考。这个值是权衡：太小信息可能不够，太大又引入噪声、稀释重点。

**Q9：怎么避免知识库重复入库？**

每个文件算一个 MD5 指纹，加载前和已处理文件的指纹记录比对，命中了就跳过。这样知识库可以**增量加载**——新加了文档只处理新增的，不用每次全量重跑。

**Q10：怎么约束模型不"编造"（减少幻觉）？**

RAG 的总结 Prompt 里做了强约束："回答必须完全基于参考资料中的信息，不编造、不添加未提及的内容、不做主观推断、只输出概括内容本身"。让模型在"有据可依"的前提下回答。

### 3.3 中间件 / 动态提示词

**Q11：LangGraph 的 middleware 是干嘛的？你用了哪几种？**（高频）

middleware 是横切逻辑，能在"调用模型前"和"调用工具前后"插入自定义处理。我用了三种：
- `wrap_tool_call`：包装工具调用，做**工具调用监控**（记录调了哪个工具、传了什么参数、是否成功）
- `before_model`：模型调用前打日志
- `dynamic_prompt`：每次生成前动态决定用哪套系统提示词

**Q12：动态提示词切换是怎么实现的？为什么要做？**

场景触发：当用户要生成"使用报告"时，Agent 会先调用 `fill_context_for_report` 工具，这个工具本身不返回内容，但会在中间件的 `wrap_tool_call` 里往 `runtime.context` 写一个 `report=True` 标志；随后 `@dynamic_prompt` 装饰的函数每次生成前读这个标志，`True` 就加载"报告写手"提示词，否则加载"客服"提示词。

为什么要做：客服和报告是两个差异很大的场景，如果揉在一套提示词里会互相干扰。动态切换让两套业务逻辑解耦、各自精准。

**Q13：`report` 场景下，Agent 的固定执行流程是怎样的？**

Prompt 里对报告生成做了强约束，必须严格走：**获取用户 ID → 获取报告月份 → 调用 fill_context_for_report → 调用 fetch_external_data 拉取使用记录 → 生成报告**。而且明确"未调用 fill_context_for_report 就禁止后续 fetch 操作"，保证上下文注入先发生。

### 3.4 评测体系（最能拉开差距的部分）

**Q14：你怎么评估一个 Agent 好不好？**（高频）

搭了一套离线评测：自己建了 42 条多场景测试集（选购/维护/故障/天气/报告五类），跑一遍 Agent 收集工具调用、最终回答和延迟，再用 LLM-as-Judge 打分，最后量化这些指标：任务完成率、工具调用准确率、检索命中率、报告格式合规率、首字/端到端延迟、平均工具调用次数。

**Q15：LLM-as-Judge 是什么？有什么问题？**（高频）

就是拿一个大模型当"裁判"，按统一标准给 Agent 的回答打分（是否完成任务、有没有幻觉），比纯人工标注快。但它有两个问题：
1. **自我偏好**：用同款模型评自己的回答会虚高，严格做法是换独立的更强模型当裁判；
2. **信息不对称**：裁判只看到我给的"参考要点"，看不到工具返回的真实数据，容易把"工具带回来的具体数字"误判成编造。

**Q16：你测出来的幻觉率是多少？怎么处理的？**（⭐⭐ 很可能被追问，重点准备）

诚实答：初版测出来偏高（59% 左右），但深挖逐条裁判理由后发现是**评测设计缺陷，不是模型真的幻觉那么多**。比如天气用例里，`get_weather` 工具返回了"26°C、湿度 50%、AQI 21"，裁判只看到我写的概括性参考要点（"给出天气信息"），就把这些具体数字当成"无依据的事实"标成幻觉了。

这件事给我的教训是：**评测指标本身的可靠性也要验证**——裁判的"参考答案"必须包含真实工具数据，否则测出来的数字是错的。正确做法是把工具返回结果也喂给裁判。

**Q17：你的评测里，工具调用准确率怎么算的？**

每条用例预先标注了"应该调用哪些工具、参数是什么"，跑完后拿 Agent 实际调用的工具名+参数去比对，命中的比例就是准确率。这个指标不依赖裁判，是纯程序比对，所以最可信，实测 100%。

### 3.5 工程化 / 模型接入

**Q18：为什么对话模型走 OpenAI 兼容接口、向量模型走原生接口？**（⭐⭐ 很加分，真实踩坑）

这是项目里真实踩过、也解决了的坑。DashScope（百炼）的新一代模型有两种调用方式：原生 SDK 接口和 OpenAI 兼容接口。实测发现：兼容接口的 `/embeddings` 对 embedding 模型有输入格式 bug（报 `input.contents` 格式错误），只有原生 `dashscope.TextEmbedding` 才能正确调用 `qwen3.7-text-embedding`；而对话模型走兼容接口没问题。所以我用工厂模式把两种接口抽象掉，对话走 `ChatOpenAI`、向量走 `DashScopeEmbeddings`，切换只改 YAML 配置。

**Q19：工厂模式在这里有什么好处？**

统一管理 LLM 和 Embedding 两个实例的创建。换模型、换接口、调温度都只改配置，业务代码（Agent、RAG）完全无感知，零改动。

**Q20：你在这个项目里还处理过什么细节坑？**

一个典型的是 embedding 的批大小：`qwen3.7-text-embedding` 单次最多 20 条，而 `DashScopeEmbeddings` 对不认识的模型默认按 25 条一批发，会导致入库报"batch size should not be larger than 20"。我封装了一个自定义 embedding 类，把 `embed_documents` 手动拆成 ≤20 一批再发。

### 3.6 流式输出 / 前端

**Q21：流式输出怎么实现的？**

后端 Agent 用 LangGraph 的 `stream(mode=["updates","messages"])` 双模式：`messages` 模式拿 token 级流、算首字延迟；`updates` 模式拿完整的工具调用和最终回答。前端 Streamlit 用 `write_stream` 逐字渲染，配合 `time.sleep` 做打字机效果。
